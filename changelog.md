## v3.12 — 2026-11-10

- `rutube_parser.py`: исправлен шаблон поиска ссылок. Возвращён строгий `[0-9a-f]{32}`, чтобы гарантированно отсечь пагинацию (`page-2` и т. п.).
- `config.ini` и `readme.md`: задокументирован параметр `max_duration` (лимит времени на парсинг).
- Обновлена документация (`rules-project.md`).

## v3.11 — 2026-11-10

- `redmine_commenter.py`: длинный текст теперь разбивается на несколько комментариев (`max_comment_length`, по умолчанию 50000 символов). Это обходит лимит Redmine на размер поля `notes` (65535 символов для MySQL/TEXT).
- `redmine_commenter.py`: ввод текста в поле `#issue_notes` переведён с `send_keys` на прямую установку значения через JavaScript. `send_keys` для больших текстов работает очень медленно и может обрываться.
- Обновлена документация (`readme.md`, `config.ini`, `rules-project.md`).

## v3.10 — 2026-11-10

- `rutube_parser.py`: исправлено регулярное выражение для поиска ссылок. Теперь используется строгий шаблон `([0-9a-f]{32})`, который соответствует только валидным 32-символьным ID видео и Shorts. Служебные страницы (пагинация `page-2` и т. п.) игнорируются.
- `redmine_commenter.py`: уточнены комментарии к коду. В комментарий Redmine отправляется только таблица (часть до разделителя `--- SENT ---`), сам разделитель и отправленные строки не попадают.
- Обновлена документация (`readme.md`, `config.ini`, `rules-project.md`).

## v3.9 — 2026-11-10

- `rutube_parser.py`: в `output_file` добавлен разделитель `--- SENT ---`. Файл теперь состоит из pending-таблицы, разделителя и sent-таблицы.
- `rutube_parser.py`: новые ссылки добавляются только в pending; ссылки, уже находящиеся в pending или sent, повторно не добавляются.
- `redmine_commenter.py`: при чтении файла с разделителем берётся только pending-часть. После успешной отправки pending перемещается под разделитель.
- `redmine_commenter.py`: чтение содержимого файлов отложено до момента отправки (после запуска парсеров). Валидация существования файлов осталась при старте.
- `redmine_commenter.py`: если все файлы с разделителем не содержат новых записей, задача пропускается без ошибки (в сводке — «пропущено»).
- `max_items` в `[rutube]` теперь ограничивает количество новых записей за прогон; старые записи (pending и sent) сохраняются.
- Обновлена документация (`readme.md`, `config.ini`, `rules-project.md`).

## v3.8 — 2026-11-10

- `rutube_parser.py`: `output_file` теперь дополняется, старые записи сохраняются. Шапка таблицы одна; новые строки добавляются к существующим.
- `max_items` теперь ограничивает количество **новых** записей за прогон, а не общее количество в файле. При `sort_by_date = true` лимит применяется к новым записям после их сортировки по дате; при `sort_by_date = false` сбор новых останавливается при достижении лимита.
- `sort_by_date = true` сортирует всю таблицу (старые + новые) по дате; `sort_by_date = false` сохраняет порядок старых записей и добавляет новые в конец.
- Обновлена документация (`readme.md`, `config.ini`, `rules-project.md`).

## v3.7 — 2026-11-10

- В `rutube_parser.py` исправлена логика прокрутки и проверки стабильности: возвращен метод `window.scrollTo` (надежно работает с виртуальным скроллом Rutube), а стабильность определяется по количеству ссылок на видео/shorts в DOM (а не по общему числу тегов `<a>`).
- Обновлена документация (`readme.md`, `rules-project.md`).

## v3.6 — 2026-11-10

- В `rutube_parser.py` переработана логика сбора: скрипт теперь явно посещает вкладки `/videos/` и `/shorts/` канала (они содержат больше информации, чем главная страница).
- В `rutube_parser.py` исправлена логика бесконечной прокрутки: вместо `window.scrollTo` используется `scrollIntoView` последнего найденного элемента, а стабильность страницы определяется по количеству элементов в DOM. Это корректно работает с виртуальным скроллом Rutube.
- Обновлена документация (`readme.md`, `rules-project.md`).

## v3.5 — 2026-11-10

- В `config.ini` уточнён комментарий к `max_items`.
