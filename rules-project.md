# Правила проекта: redmine_commenter

Версия v3.1. Работает совместно с rules-common.md. Универсальные правила выше правил этого файла (см. правило 9.2 в rules-common.md).

## Преамбула (для ассистента)

Этот документ — правила конкретного проекта. Прочитай его целиком вместе с rules-common.md до ответа на первую задачу.

- Универсальные правила в rules-common.md действуют полностью.
- Всё, что ниже, — специфика проекта.
- Если правило ниже противоречит универсальному — действуй по универсальному и укажи на конфликт.
- Новое универсальное правило, которого нет в rules-common.md, записывай в rules-proposal.md.

## 1. Название и назначение

- Название: redmine_commenter
- Назначение (1–2 предложения): добавляет комментарии к нескольким задачам Redmine через браузер, когда REST API и приём почты недоступны. Для каждой задачи текст собирается из одного или нескольких локальных файлов; перед задачей могут запускаться парсеры (сейчас — Rutube, в будущем — соцсети и мессенджеры).
- Пользователь результата: владелец учётной записи Redmine с обычными правами.

## 2. Адрес репозитория

- Адрес: `https://github.com/butko/python-redmine-comments`

## 3. Стек и среда

- Язык и версия: Python 3.10+
- Внешние библиотеки: Selenium 4.x (единственная внешняя зависимость)
- Платформа запуска: Astra Linux
- Целевой браузер: Chromium (`/usr/bin/chromium`). Альтернативы — Google Chrome, Яндекс.Браузер.
- Ограничения целевой среды: графическая сессия (X11/Wayland). Системный Python защищён PEP 668. Требуется драйвер, мажорная версия которого совпадает с версией браузера.
- Способ установки зависимостей: `venv`. Команды — в `readme.md`.

## 4. Схема работы

- Вариант (по правилу 6.6): отдельный файл с изображением (`scheme.svg`).
- Встроенная текстовая схема (Mermaid) пока не используется из-за сложности ветвления алгоритма (парсеры, браузер, отправка частями).

### Локальные файлы (не входят в проект)

Эти файлы создаются автоматически при работе программы. Они не являются файлами проекта: не версионируются, не публикуются. В документации описаны для того, чтобы было понятно, что появится на диске.

- драйверы (`chromedriver`, `yandexdriver`) — скачиваются пользователем отдельно;
- тексты комментариев (например, `comment.txt`) — пользователь создаёт сам или они готовятся заранее;
- результаты парсеров (например, `rutube_links.txt`) — создаются автоматически при запуске парсера, дополняются;
- `config.ini` — рабочий конфиг с реальными данными (создаётся пользователем из `config.template.ini`);
- `browser_profile/` — выделенный профиль браузера, создаётся автоматически;
- логи (`redmine_commenter.log`, `rutube_parser.log`, `chromium_login.log`) — создаются автоматически при каждом запуске;
- вспомогательные локальные скрипты (например, `bash.txt`).

## 6. Команды запуска

- Обычный прогон: `python3 redmine_commenter.py`
- Вход в Redmine: `python3 redmine_commenter.py --login`
- Один парсер через основной скрипт: `python3 redmine_commenter.py --prepare <имя>`
- Все парсеры через основной скрипт: `python3 redmine_commenter.py --prepare-all`
- Проверка окружения: `python3 check_env.py`
- Парсер напрямую: `python3 rutube_parser.py` (конфиг по умолчанию) или `python3 rutube_parser.py --config <путь>`

**Про `--config`.** Во всех командах параметр необязателен. По умолчанию скрипты ищут `config.ini` рядом со собой, независимо от текущего каталога. Путь можно переопределить явно.

## 7. Правила, специфические для проекта

- **Режим `auto`.** Порт 9222 отвечает как DevTools → attach; иначе launch выделенного экземпляра с `profile_dir`.
- **Выделенный профиль.** `profile_dir = ./browser_profile`. Не конфликтует с основным браузером. Локальный артефакт.
- **`--login` и отсоединение.** `subprocess.Popen(..., start_new_session=True)`. Адрес — `login_url` из `[redmine]`, если задан.
- **Задачи — секции `[task:<метка>]`.** Порядок секций = порядок обработки. Метка — для логов.
- **Параметры задачи.** `issue_url` (обязательно), `prepare` (список парсеров через запятую), `comment_files` или `comment_text`. Файлы из `comment_files` — локальные: создаются пользователем или парсерами.
- **Парсеры — секции `[prepare:<имя>]`.** Параметры: `script` (обязательно), `args`, `timeout` (по умолчанию 600). Парсер получает `--config <путь>` и читает свою секцию (например, `[rutube]`).
- **Контракт парсера.** Принимает `--config` (необязательный, по умолчанию `config.ini` рядом с парсером), пишет результат в локальный `output_file`, возвращает код 0 при успехе. Ничего не знает про Redmine.
- **Формат результата парсера Rutube.** Таблица Textile для Redmine (`|_.Дата публикации|_.Заголовок|_.Ссылка|`). Файл имеет структуру: pending-таблица, разделитель `--- SENT ---`, sent-таблица. Новые ссылки добавляются в pending; ссылки, уже находящиеся в pending или sent, повторно не добавляются. Ссылки очищаются от параметров плейлиста. Заголовок и дата запрашиваются через API Rutube. API может возвращать дату как timestamp или ISO-строку — парсер поддерживает оба формата.
- **Логика сбора парсера Rutube.** Парсер явно открывает вкладки `/videos/` и `/shorts/` канала. Прокрутка выполняется через `window.scrollTo`. Строгий regex `[0-9a-f]{32}` отсекает пагинацию.
- **Параметр `max_items` (для Rutube).** В секции `[rutube]` можно задать ограничение количества **новых** записей, добавляемых за один прогон (видео + Shorts). Старые записи (pending и sent) сохраняются и не удаляются. Если `sort_by_date = true`, лимит применяется к новым записям ПОСЛЕ их сортировки по дате (чтобы добавить самые новые из новых). Если `sort_by_date = false`, сбор новых останавливается при достижении лимита.
- **Параметр `max_duration` (для Rutube).** В секции `[rutube]` задаёт максимальное время работы парсера в секундах (0 — без ограничений). Если сбор затягивается, скрипт остановится и сохранит то, что успел собрать.
- **Параметр `sort_by_date` (для Rutube).** В секции `[rutube]` управляет сортировкой pending-части. `true` — pending (старые + новые) сортируется по дате (самые новые сверху); `false` — старые pending сохраняют порядок, новые добавляются в конец в порядке сбора. Часть sent не сортируется.
- **Разделитель `--- SENT ---`.** Файлы из `comment_files` могут содержать этот разделитель. `redmine_commenter.py` при чтении берёт только часть до разделителя (pending). После успешной отправки pending перемещается под разделитель. Если pending пуст (только шапка), файл пропускается; если все файлы такие — задача пропускается без ошибки.
- **Чтение файлов отложено.** Содержимое `comment_files` читается после запуска парсеров, непосредственно перед отправкой. Валидация существования файлов — при старте. Это позволяет парсерам обновлять файлы в том же прогоне.
- **Ввод текста через JavaScript.** Текст в поле `#issue_notes` устанавливается прямой установкой `value` через JavaScript, а не через `send_keys`. `send_keys` эмулирует нажатия клавиш и для больших текстов работает очень медленно или обрывается. JS-вставка мгновенна.
- **Разбиение длинного текста.** Если текст превышает `max_comment_length` (по умолчанию 50000 символов), он разбивается на несколько частей, каждая отправляется отдельным комментарием. Это обходит ограничение Redmine на размер поля `notes` (65535 символов для MySQL/TEXT).
- **Per-task режим (по умолчанию).** Перед задачей запускаются только её парсеры. Кэш на прогон: успешно отработавший парсер повторно не запускается. Упавший парсер → задача пропускается, остальные обрабатываются (fail-soft на уровне задачи).
- **Глобальный режим (`prepare_all = true`).** Все парсеры, на которые ссылается хотя бы одна задача, запускаются до цикла в порядке объявления `[prepare:*]`. Задачи, чьи парсеры упали, пропускаются.
- **Отдельные режимы запуска парсеров.** `--prepare <имя>` и `--prepare-all` запускают парсеры без Redmine (для тестирования). Парсеры также запускаются напрямую.
- **Валидация на старте, fail-fast.** Все задачи, `issue_url`, существование файлов `comment_files` и ссылки `prepare` на существующие `[prepare:*]` проверяются до открытия браузера. Ошибка — код 1, браузер не открывается.
- **Отказоустойчивый цикл.** Ошибка в задаче или её парсере не останавливает остальные. В конце — сводка и код 1, если что-то упало.
- **Сборка текста.** Непустые файлы соединяются через `\n\n`, обрезка по краям, пустые файлы пропускаются с предупреждением.
- **Поиск драйвера.** `chromedriver` → `yandexdriver` в папке скрипта → `driver_path` → Selenium Manager.
- **Структура страницы Redmine.** Поле `#issue_notes` внутри `#update`. Форма открывается через `showAndScrollTo`. Submit-кнопка — строго в `#issue-form`. Подтверждение — появление текста в `#history`.
- **Обезличивание.** В шаблонах и примерах — `example.com`, `example_channel`, `your_login`, `<метка>`. Это распространяется на `config.template.ini`, `readme.md`, `rules-project.md`, `scheme.svg`. Реальные URL и имена — только в рабочем `config.ini`, который не публикуется. При добавлении примеров в документацию сначала проверять, что значения обезличены (правило 3.4 в rules-common.md). Адрес репозитория проекта — исключение по правилу 6.15: в `readme.md` и здесь указывается фактический адрес.
- **Локальные файлы не входят в проект.** Файлы, которые создаются автоматически (драйверы, тексты комментариев, результаты парсеров, профиль браузера, логи, `config.ini`), описываются в документации, но не считаются файлами проекта: они не версионируются и не публикуются.
- **Документация обновляется сразу, а не по запросу.** При любом изменении кода, конфига, структуры или поведения программы `readme.md`, `changelog.md`, `rules-project.md` и (при необходимости) `scheme.svg` обновляются в том же ответе. Отдельного запроса не требуется. Уточнение к 6.12: проверка актуальности — при каждом изменении, а не «при завершении этапа». Версии поднимаются по 10.6.

## 8. Ограничения проекта

- Подключиться к запущенному браузеру без `--remote-debugging-port` невозможно — фундаментальное ограничение Chrome/Chromium. Решается выделенным профилем.
- Селекторы Redmine могут меняться при обновлении или смене темы; скрипт рассчитан на `theme-Classic`.
- 2FA/SSO с интерактивной проверкой на каждом запуске не поддерживаются.
- Для `launch` (и `auto`, когда порт не слушается) на первом запуске нужен `--login`.
- Драйвер и браузер должны иметь совпадающие мажорные версии.
- **Старый формат конфига (v1.x) не поддерживается.**
- **Fail-fast валидация на старте.** Ошибка в любой задаче — браузер не открывается.
- **Сборка текста фиксирована** (`\n\n`, обрезка). Кастомизация — правка кода.
- **Парсеры — отдельные скрипты.** Добавление нового парсера требует: новый скрипт, секции `[prepare:<имя>]` и `[<имя>]`, запись в `readme.md`. Основной скрипт при этом не меняется. Это сделано намеренно, чтобы каждый следующий парсер был отдельным этапом.
- **Парсеры зависят от вёрстки источников.** При изменении структуры Rutube (и будущих соцсетей) парсеры могут перестать находить ссылки. Шаблоны URL вынесены в код парсера, но не в конфиг.
- **Кэш на прогон.** Один и тот же парсер не запускается дважды за прогон. Если нужен «свежий» результат для каждой задачи — разделите задачи на отдельные прогоны.
- **Зависимость от API Rutube.** Если API недоступен, заголовки и даты в таблице будут пустыми. Ссылки при этом сохраняются корректно.
- **Лимит Redmine на размер комментария.** Поле `notes` в MySQL имеет тип `TEXT` с максимальной длиной 65 535 символов. Скрипт разбивает текст на части по `max_comment_length`, чтобы не упереться в этот лимит.
- `browser_profile/` содержит cookie-сессию — не публиковать.
